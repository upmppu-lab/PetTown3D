# PetTown3D 통합 개발 — 1단계 실제 프로젝트 분석
분석일: 2026-10-25
대상: C:\UnityProjects\PetTown3D / Unity 6000.6.6f1
최신 지시서: UI·자연환경·펫샵 인테리어·건물 증축 통합 개발 지시서.

## 확인한 현재 상태와 작업 경계
Unity MCP에서 활성 프로젝트 PetTown3D, 씬 PetTown3D_CharacterTest, URP 자산 Assets/PetTown3D/Settings/PetTown3D_URP.asset을 확인했다. 편집 모드 최상위 오브젝트는 PetTown3D_GAME, PetTown_MasterCharacter 두 개이며 Canvas와 마을 대부분은 Play 시작 시 생성된다. 최종 확인 시 Play 중지, 컴파일/Import 대기 없음, 씬 isDirty=false였다.
이 보고서는 새 통합 지시서의 1단계 분석이다. UI·실내·증축·자연환경 게임 코드는 새로 수정하지 않았다. 앞서 승인된 건설 계획의 5·6단계 변경은 별도 완료 보고서에 분리했다.
이후 별도로 허용한 OBJ Import 검증은 수행했다. Unity가 미등록 에셋 폴더도 등록하면서 .meta/Import 캐시가 추가됐으며 원본 OBJ/MTL, 게임 코드, 씬은 변경하지 않았다. 무료 다운로드·압축 해제·Import에 대한 일상 작업 권한은 확인했다. 이번 분석을 위해 외부 에셋을 새로 다운로드하지는 않았다.

## 1. 펫샵의 실제 구조와 크기
PetTownGame.CreateBuilding(kind=0)가 펫샵을 생성한다. 기본 바닥 크기는 15×15m, 명목 면적 225m²이다. 현재 실내 기준 높이는 건물 바닥 기준 +0.12m이다.
BuildModularShopShell은 기존 Barking_Dog의 Resources/Modular/Floor_01, Wall_Simple_01, Roof_01을 사용한다. 3m 모듈로 바닥 5×5=25장과 뒤·왼쪽 벽 각 5개를 구성한다. 현재 열린 매장 형태로 앞·오른쪽은 열려 있고 지붕은 Toggle_Roof로 표시를 제어한다. 단순한 폐쇄형 4벽 건물로 가정하면 안 된다.
MCP에서 기존 Floor_01은 3×3m 평면, Wall_Simple_01은 약 0.25×3×3m로 확인했다. prefab 누락 시만 기존 큐브 셸로 대체한다.
펫 카페·병원은 현재 11×10m 절차적 바닥/벽이며 같은 완성 건물 prefab을 통째로 배치하는 구조가 아니다. 일반 주민 주택은 별도의 닫힌 imported 모델이다.

## 2. 현재 벽·바닥·가구 배치
벽/바닥은 CreateBuilding, BuildModularShopShell, Part/Deco로 만든다. buildingFloors와 flatZones가 캐릭터 바닥 높이, 평탄화, 건설 검사와 연결된다.
가구는 CreateFurniture의 6종(Resources/Furniture/FurnCounter, FurnPetBed, FurnDisplay, FurnChair, FurnTable, FurnPlant)과 CreatePetShopDetail의 7종 전문 진열물로 나뉜다.
기본 펫샵은 카운터/펫베드/진열대와 사료대/장난감대/RAT 케이지/수족관/개 쿠션/고양이 쿠션/새장을 배치한다. 컴퓨터·직원 의자·화분·고양이 타워가 모두 갖춰진 11종 구성이 현재 구현된 것은 아니다. 고양이 쿠션은 타워와 다르다.
전문 진열물 다수는 primitive 조합이며 수족관의 물고기는 실제 모델이다. 일부 진열물에는 BoxCollider 및 fitted NavMesh 장애물이 있어 단순 장식 교체도 통행 영향 확인이 필요하다.
추가 가구는 현재 매장 중심으로부터 12m 거리 조건과 일괄 비용 50을 사용한다. 실내 셀/가구 점유 영역에 따른 정밀 배치 시스템은 아니다. 자동 기본 가구와 플레이어 구매 가구는 props에 들어가지만 개별 저장 레코드가 없다.

대표 모델 12개를 Unity에서 읽어 URP/Lit 지원과 bounds를 확인했다. 모델마다 원본 단위가 다르다. 예를 들어 kitchenBar 약 4.3×4.2×2.1, computerScreen 약 3.927×2.943×1.04, KayKit chair_A 약 0.75×1.258×0.845, Kenney building floor 2×0.1×2m, wall 0.1×2.4×2m이다.
따라서 원본 Transform을 무작정 같은 scale로 쓰면 안 된다. 원본은 보존하고, 모델별 미터 환산·피벗·바닥 접점·앞 방향을 가진 wrapper prefab/config로 정규화한다. 단위 보정과 무리하게 작게 축소해 밀어 넣기는 구분해야 한다.
Kenney/KayKit 및 Nature 팩의 로컬 License에서 CC0를 확인했다. Furniture Pack 2017 폴더에는 별도 라이선스 문서를 찾지 못했으므로 출처 확인 전 우선 채택 대상에서 제외한다.
해당 팩의 .blend 23종은 Blender 미설치 오류를 발생시킨다. FBX/OBJ 대체본이 있으므로 당장 Blender를 설치할 필요는 없다. 원본 .blend를 삭제하거나 이동하지 않았다.

## 5. 초기 인테리어를 개선하는 안전한 방법
225m²는 11종을 검토할 충분한 명목 면적이다. 아직 실제 동선 검증 없이 초기 건물을 키워야 한다고 결론 내릴 근거는 없다.
주 출입구 앞 2m 정도, 주 동선 1.5~2m, 보조 동선 최소 약 1.2m를 먼저 남기는 설계 시안을 권장한다. 계산대·컴퓨터·직원 의자 묶음, 양 벽 진열대, 후면 케이지/수족관, 반대편 펫 휴식 영역으로 구역을 나눈다. 수치는 시안 기준이며 실제 NPC 에이전트 반경/가구 bounds와 대조한다.
기본 가구 카탈로그와 배치 프리셋을 데이터로 만들고 신규 건설에만 적용한다. 기존 마을의 가구는 opt-in 업그레이드/마이그레이션 없이 재생성하거나 초기화하지 않는다.
특히 가구 저장 기반을 먼저 연결해야 한다. 새 카탈로그에서 사라졌다는 이유로 기존 객체를 삭제하지 말고 legacy ID와 레코드를 보존한다.

## 6. 증축을 위한 벽·바닥 모듈화
기존 3m 셸을 우선 재사용한다. 최초 증축 단위는 예를 들어 3m 깊이의 줄이며 15m 전체 변을 늘리면 45m²가 추가된다. 가격은 결정하지 않고 건물 종류별 면적 단가/고정비 데이터로 둔다.
Kenney Building의 2m 모듈은 기존 3m와 바로 맞지 않는다. 원본 교체부터 하지 말고, 1m 논리 셀 위에서 2m/1m half 모듈을 조합하는 adapter를 테스트하거나 기존 3m 셸의 시각 변형에 한정해 사용한다. 기존 15m를 억지로 16m로 바꾸지 않는다.
실내는 root 고정 + local cell 집합/영역으로 저장한다. 왼쪽만 늘어나면 영역 중심이 root에서 벗어나므로 현재의 'root 중심 + WorldFootprint 크기' 하나만 확장하는 것으로는 부족하다. 비대칭 local bounds 또는 점유 셀을 별도로 관리해야 한다.
바닥 셀 합집합의 경계에서 외벽을 계산하고, 붙는 이전 외벽만 갱신한다. 가구 부모/ID/로컬 좌표와 생존 객체는 유지한다. 건물 전체 Transform Scale을 키우거나 CreateBuilding으로 통째로 재생성하지 않는다.

## 7. 방향 및 부지 검사
기존 Rotation/entranceBaseYaw/출입구 보정에 따라 전후좌우를 월드로 변환한다. 월드 X/Z로 고정하거나 Euler 값만 보고 앞 방향을 가정하지 않는다.
추가되는 셀과 평탄화 영향 구역만 검사하고 자기 건물의 기존 영역은 소유 ID로 제외한다.
- 초록: 비용/경사/수역/건물/도로/출입구/통행로 모두 통과.
- 노랑: 이동/제거 가능한 나무·수풀·화분·장식물 때문에 현재 확정 불가. 플레이어가 정리한 뒤 재검사.
- 빨강: 다른 건물, 도로, 강, 범위 밖, 위험 경사, 중요 통로 차단.
증축에서 기존 ClearPropsAndRoadsInFootprint를 그대로 호출하면 안 된다. 이 메서드는 식생을 삭제하므로 자동 제거 금지 조건과 충돌한다. 도로도 자동 재배치/삭제하지 않는다.
NaturePlacementRecord에 stable ID, prefab ID, 위치/크기, 장식/충돌 분류, 이동/제거 가능 여부를 기록하면 배치와 증축 검사를 공유할 수 있다. 초기 건설에서 미래 확장 부지를 강제로 예약하지 않는다.
기존 NavMesh와 4단계 안전 검사 기반을 재사용하되, 확장된 바닥·입구·통로의 실제 경로를 확인하고 완료 후만 갱신한다.

## 8. 골드 결제와 저장 설계
기존 money와 PetTown3D_Save를 재사용하며 새 통화/플레이어 레벨 시스템을 만들지 않는다. 기존 shopLevel 업그레이드는 매장 레벨/재고 해금이며 실내 증축이 아니다. 증축에 플레이어 레벨 제한을 붙이지 않는다.
현재 SaveData는 건물/재화/펫 재고를 저장하지만 props의 추가 가구 위치/회전은 저장하지 않는다. 재실행 시 기본 가구를 다시 생성한다. 따라서 '기존 가구가 재시작 후 그대로 남는다'는 상태가 아직 보장되지 않는다.
선택적 확장 필드로 buildingId, local room cells/bounds, expansion history, entrance ID, furniture records(id/owner/catalog/local position/rotation/state/default 여부)를 추가하고 기존 types/x/z, constructionVersion, roadVersion은 유지한다.
기본 레이아웃은 해당 건물에 가구 레코드가 없는 legacy 저장일 때만 한 번 생성한다. 새 저장의 가구 로드 시 기본 가구를 중복 생성하지 않는다. 알려지지 않은 catalog ID도 원본 레코드는 유지한다.
확정 순서: 계획/비용/최신 부지 재검사 → 비활성 모듈 준비 → 기존 상태 스냅샷 → 바닥/벽 적용 및 가구·충돌/경로 확인 → 성공 시 비용 차감 및 저장. 실패 시 신규 모듈 제거, 기존 벽/영역/가구/코인/저장 문자열을 복구한다. 지형을 바꿔야 하면 mesh 정점과 flatZones도 되돌릴 준비가 필요하다.
PlayerPrefs는 다중 작업 트랜잭션 저장소가 아니므로 '차감하고 중간 실패해도 안전하다'고 가정하면 안 된다. 새 파일 저장 시스템으로 임의 교체하지 않고 현재 저장 문자열 안의 추가 필드와 롤백부터 설계한다.

## 9. 건물 이전 기능
현재 건물 이전/가구 이동·회전 레코드 시스템은 찾지 못했다. 플레이어 이동이나 신규 배치 회전과는 다르다.
이번에는 설계만 한다. 고정 buildingId와 로컬 실내 레이아웃/가구 상태를 보존하면 향후 건물 root 이전 후 월드 충돌·입구·도로 연결을 재검사할 수 있다. 카페·병원은 같은 실내 모델 인터페이스를 쓰되 상세 시설/기능은 만들지 않는다.

## 10. 현재 HUD와 Kenney UI 활용 계획
현재 HUD는 PetTownGame.BuildUI/BuildStatusBar/BuildNavBar/BuildActionPanel/BuildToast/BuildOrderCard가 생성하는 uGUI다. PetTown_ModernCanvas, StatusTitle/Sub, CoinText, NavBar, ActionPanel, Toast, OrderCard, PlacementDirectionHint, ConstructionTools가 주요 런타임 객체다. 편집 모드에 Canvas가 없다고 UI 미구현으로 판단하면 안 된다.
UnityEngine.UI.Text + NanumSquareB를 사용하며 TMP가 아니다. CanvasScaler 1280×720, match 0.5, sortingOrder 100이다. 현재 메뉴는 탐험/건설/꾸미기/커스텀/상점 5개다. 재화, Day, 주민 수, 명성, 펫 주문/재고, 저장, 지붕 보기가 실제 기능이며 플레이어 XP/경험치바나 일반 아이템 가방은 확인되지 않았다. OnGUI는 처음에 return하므로 아래 오래된 HUD 코드를 현재 활성 UI로 착각하지 않는다.
Kenney UI Pack에는 PNG 870개(Preview/Sample 포함), SVG 434개, TTF 2개, OGG 6개가 있다. Blue/Green/Grey/Red/Yellow, Default/Double 변형, 사각/둥근 버튼·화살표·체크/닫기·슬라이더·별을 활용할 수 있다. 완성된 창 prefab이나 독립 panel 이름의 PNG는 없다. button_rectangle_border 등을 9-slice 프레임으로 재사용한다. 펫/건물 전용 아이콘이 모두 들어 있다고 가정하지 않는다.
확인한 button_rectangle_flat은 256×64, TextureImporter Default, border 0이다. 선택한 PNG만 Sprite/9-slice용 wrapper 또는 런타임 Sprite로 준비하며 원본 PNG는 보존한다. TMP 패키지/영문 SDF 폰트는 존재하지만 확인한 LiberationSans SDF는 '가' 글리프가 없었다. 기존 NanumSquareB 소스로 한글 TMP font/fallback을 생성해야 한다.
기존 Canvas는 새 창/HUD 검증까지 남긴다. feature flag와 CanvasGroup/입력 차단 전환으로 두 UI가 중복 클릭을 받지 않게 한다. 메뉴·버튼은 기존 SetMode/OnNavClick/선택 상태/저장 동작에 연결한다. 기존 캐릭터 커스터마이징 Canvas, 클릭 차단, 카메라 입력과 충돌하지 않게 검증한다.

## 11. 공통 목록창과 실제 데이터 연결
독립 공통 창 프레임에 제목/닫기/탭/검색/정렬/ScrollRect/카드/상세 영역을 두고 데이터 provider만 교체한다.
- 건물: types/costs, PetTownBuildingDefinition 및 실제 footprint/방향 정보를 읽는다. Pet Shop은 최초 건설 전용, Road는 m당 비용/드래그 도구이므로 일반 건물 복제 상품처럼 처리하지 않는다.
- 가구: FurnitureResource/Height와 전문 가구 카탈로그를 통합하되 기존 배치 진입점을 재사용한다. 가격/면적/이름 검색·정렬은 실제 필드에 한정한다.
- 썸네일: 현재 GetItemIcon의 실제 가구 prefab RenderTexture 캐시를 재사용할 수 있다. 주민 주택 등 실제 모델 prefab은 그대로 미리보기 가능하다. 다른 건물은 절차적으로 만들어지므로 전체 prefab이 있다고 가정하지 않는다. 임시 썸네일을 만들려고 CreateBuilding을 호출하면 지형/가구/저장에 부작용이 생길 수 있다. 기존 생성 객체의 안전한 시각 복제 또는 분리된 순수 visual preview가 필요하다. 준비 전에는 이름/설치 면적을 정직하게 표시한다.
- 가방: 현재 inventory는 dogStock+catStock+rabbitStock의 합계이며 일반 아이템 ID/스택/수량/사용 효과 데이터가 아니다. 가짜 인벤토리를 만들지 않는다. 우선 펫샵 재고를 관리창에 표시하고 일반 가방은 미구현으로 구분한다.
- 주민/펫: villagers/livePets의 실제 런타임 목록은 읽을 수 있으나 이름·상세 상태·개체별 영속 데이터는 별도 검토가 필요하다. 숫자만으로 가짜 주민 프로필을 만들지 않는다.
- 펫샵 관리: 현재 주문, 펫 재고, 매장 레벨, 재화, 저장/지붕 보기와 연결. 증축하기는 실제 기능이 완성되기 전 작동하는 것처럼 표시하지 않는다. 카페·병원 상세 기능은 이후 범위다.
작은 현재 목록에 대규모 가상화부터 도입할 필요는 없다. 썸네일은 선택/스크롤 시 지연 생성하고 해제/재사용 규칙을 둔다. PC 1280×720/1920×1080, 좁은 화면/모바일 safe area와 최소 터치 영역을 검증한다.

## 12. 현재 지형·강·도로·충돌
Unity Terrain이 아니라 BuildWorld의 110×110 셀, 2m 간격, 220×220m Procedural Mesh다. 정점 12,321개, 삼각형 24,200개이며 MeshCollider를 공유한다.
GroundBlend_MAT의 PetTown/GroundBlend(URP) 셰이더가 정점 RGBA 가중치로 흙/성긴 풀/짙은 풀/헤더 4개를 혼합한다. 원본 텍스처는 TerrainDemoScene_HDRP의 사진 계열 TIF이며 폴더명과 무관하게 텍스처 자체는 URP에서 사용할 수 있다. 현재 tint는 약 (1.3,1.3,1.1)이다.
현재 강 중심선은 x=sin(z×0.031)×12+sin(z×0.09)×3이다. z=-109~109를 0.5m 간격으로 샘플링하며 수면 폭 10.4m, 횡단 32분할, 높이 -0.18m다. 강 지형은 반폭 5.25m까지 -0.90m 강바닥, 외측 9m까지 원래 높이로 부드럽게 복귀한다. 이 완만한 단면은 과거 톱니 강둑 방지를 위해 중요하다.
River_Terrain_Conforming_Banks는 실제 지형 메시를 공유하는 얇은 렌더 오버레이다. 별도로 만든 거친 강둑 메시로 교체하면 틈/톱니가 다시 생길 수 있다.
PetTownRiverSurface.shader는 현재 전면 블러가 없다. 중앙 alpha는 1이고 물 가장자리만 약 8cm 페이드된다. 실제 깊이를 정점 색으로, 얕은 물~청록 중앙 색상으로 표현한다. UV.y는 강의 누적 거리/5m이며 시간에 따라 phase를 바꿔 중심선을 따른 물결을 움직인다. 현재 0.035주기/s는 파장 5m 기준 약 0.175m/s의 시각적 흐름이다. 실제 유체 시뮬레이션은 아니다.
게임 수역 검사는 오래된 IsWater의 가로 반폭 3.5m 및 호수 사각형, 건설 검사는 넓어진 시각 수면에 대한 별도 안전 여유를 사용한다. 물 외형 폭을 함부로 바꾸면 식생/도로/NPC/건물의 수역 판정과 달라질 수 있다.
도로는 실제 지형 높이를 샘플링한 별도 메시이고 world-distance UV를 사용한다. 완료한 5·6단계의 경로 저장/직선·곡선 입력은 보존한다.
NavMeshSurface/Agent 기반이며 mesh 수집 제외와 carving 장애물, player 충돌체/지형 높이 질의가 함께 작동한다. 물 외관 교체를 이유로 기존 NavMesh/NPC 행동을 교체하지 않는다.
현재 PetTownGame/활성 씬에서 독립 다리 생성 로직이나 이름으로 확인할 수 있는 배치 다리를 찾지 못했다. 플레이어 코드에는 bridge/platform 관련 주석만 있다. 따라서 '다리를 통한 이동을 검증했다'고 보고할 수 없으며 실제 다리가 추가되거나 확인되면 월드 좌표/충돌/연결을 별도 검사한다.

## 13. 그래픽 원인과 통합 개선 권장안
### 현재 어색함의 근거
- 4장의 사진성 텍스처를 같은 UV로 알베도 혼합한다. 잔디 높이/거칠기 변화가 없어 평평한 지면 이미지로 읽히기 쉽다. 단순히 초록 tint를 바꾸는 것으로 입체감/스타일 통일이 해결되지 않는다.
- GroundBlend는 하나의 조명 pass로 단순 확산/SH를 계산하며 텍스처 주파수/명암과 원거리 반복이 도드라진다. 후처리 contrast=10, saturation=12, postExposure=0.1도 질감 대비를 키울 가능성이 있다. 후처리 수치만으로 어두움의 유일 원인이라고 단정하지 않는다.
- 현재 강둑은 흙 텍스처와 셰이더상 자갈 무늬이며 실제 작은 돌/수풀의 실루엣 변화는 부족하다. 일정한 수면 폭과 거리 띠 기반 색 경계도 인공적으로 읽힐 수 있다.
- 수면은 얕은 물/흐름 구현이 있지만 물결과 하이라이트는 주로 색상의 sin 패턴이다. 깊이 기반 투과/굴절이나 실제 반사와 같은 표현은 제한된다. 블러 제거 작업이 이미 반영된 상태이므로 다시 넓은 alpha 그라데이션을 넣지 않는다.
- 현재 나무/풀은 기존 Resources/Trees, Vegetation/UNS_* 등을 사용한다. 새 Nature MegaKit이 설치됐다는 이유로 이미 마을에 쓰이고 있다고 볼 수 없다. 식생 배치는 Ground와 오래된 IsWater를 사용하므로 실제 바닥/시각 수면/도로와의 간극이 생길 수 있다.

### A/B 비교
| 방안 | 품질 가능성 | 비용/난이도 | 기존 시스템 위험 |
|---|---|---|---|
| A: 현재 경로·지형·수면 메시 유지, 지면/강둑/수면 재질과 장식 개선 | 목표 스타일에 충분히 접근 가능. 현 곡선과 작은 페이드 유지 | 낮음~중간. 현재의 투명 pass 비용부터 관리 | 낮음. 권장 출발점 |
| B: 같은 중심선으로 수면 렌더러/메시 교체 | 깊이·반사·물결 표현 확장 가능 | 중간~높음. Depth/Opaque texture, 반사/투명 overdraw 및 모바일 검증 필요 | 중간~높음. 수역/다리/바닥 틈/정렬 영향 |
A를 먼저 별도 테스트 환경에서 비교하고, 눈에 띄는 품질 이득이 확인될 때만 B를 선택한다. 통째로 Terrain으로 바꾸거나 강 경로/지형 충돌을 교체할 이유는 없다.
이미 설치된 물 후보는 Houdisoft의 water shader ocean(UniversalPipeline), UNS_Water(URP/Lit), Polytope PT_Water(UniversalPipeline)가 있다. 실제 강 곡면 UV/수심과 맞는지는 별도 테스트가 필요하다. 이름이 HDRP인 WaterDepthBased 그래프는 실제 HDTarget이므로 현 URP에 바로 채택하지 않는다. Shader.isSupported만으로 파이프라인 호환을 보장할 수 없었다.
현재 URP 설정의 DepthTexture/OpaqueTexture는 꺼져 있다. B에서 이를 요구하면 비용을 측정하고 테스트 카메라/테스트 설정에서 먼저 검증한다. 유료 Pro 전용 기능을 무료 에셋에 있다고 가정하지 않는다.

### 안전한 통합 구현
기존 메시와 Collider, Ground, RiverCenterX, 건물 평탄화/저장 경로는 유지한다. 원본 지면 머티리얼/셰이더를 복제한 테스트 버전에 밝고 단순한 잔디/흙/돌 팔레트, 근·원거리 두 질감 스케일과 약한 반복 분산, 기존 정점 가중치/강둑 거리 마스크를 적용한다. 하나의 화면에서 잔디~흙~얕은 물~깊은 물을 함께 비교한다.
강둑은 지형 공유 오버레이를 유지하고 작은 자갈·흙 색·수풀을 제한적으로 보강한다. 수면은 좁은 가장자리 페이드와 중앙 불투명도를 유지하며 약한 normal/하이라이트 또는 검증된 기존 shader를 비교한다.
자연물은 검증된 실제 68종 중 CommonTree/Pine, Bush_Common, Grass_Common_Short, Clover, Flower, Pebble_Round/Square, Rock_Medium, RockPath 등을 쓴다. 전용 갈대가 있다고 가정하지 않는다.
Unity용 Nature 모델 68개에서 renderer material 참조 88개가 모두 URP/Lit이고 누락/미지원 shader 0, LODGroup 0이었다. 샘플 CommonTree_1은 약 6,265삼각형, Grass_Common_Short 155, Rock_Medium_1 342, Bush_Common 900삼각형이었다. 모든 모델이 저비용이라고 가정하면 안 된다. 확인한 샘플 material의 instancing은 꺼져 있다.
고정 seed + 안정 ID + 지역 밀도 제한/변형으로 배치하고 수면 여유, 실제 terrain raycast 높이, 건물/입구/도로 점유를 피한다. 미래 증축 부지를 미리 빈 땅으로 강제하지 않고 장식물 ID를 장애물 검사에 제공한다. 작은 장식 Collider는 제거하고 큰 바위만 간단 충돌체를 검토한다. 원거리 표시 제한/LOD 또는 단순화, 공유 머티리얼/인스턴싱과 드로우콜을 측정한다.
테스트 환경은 기존 씬 복제 후 GameManager를 실행하는 방식보다 별도 시각 테스트 scene/preview가 안전하다. PetTownGame.Start를 실행하면 LoadGame/SaveGame과 월드 생성이 발생하므로 테스트 미리보기에서 직접 호출하지 않는다. 실제 마을 적용은 비교 결과를 확인한 뒤 별도 단계로 진행한다.

가구 영속 저장과 실내 영역 변경은 필수적인 기존 저장/건설 연결 변경이므로 구현 전에 이 영향 범위를 기준으로 검토해야 한다. 전체 게임을 리팩터링하는 작업은 아니다.

## 15. 최신 지시서의 9단계 실행 계획
1. 전체 분석 — 본 보고서. 실제 구조/에셋/호환성과 누락·위험 확인. 완료.
2. 공통 UI·건물 목록창 — Kenney/TMP 한글, 창 프레임/카드/스크롤/선택. 기존 HUD를 남기고 건설 선택 API만 연결. 난이도 중간. 선택→미리보기→R 회전→안전 검사→설치가 기존 흐름과 같은지 검증.
3. 가구 목록·펫샵 관리 — 실제 6종+전문 진열물 데이터 정리, 가구 소유/로컬 상태 저장 기반 선행, 기존 재고/주문/관리 기능 연결. 난이도 중간~높음. 추가 가구 저장/재실행·기본 가구 중복 방지 필수.
4. 펫샵 실내 — wrapper 모델 및 11종 배치 시안, 기존 15×15m 안의 실제 동선 검증. 기본 배치는 새 건설 우선. 기존 매장 전체 재생성 금지. 난이도 중간~높음.
5. 펫샵 증축 — 로컬 방향과 고정 면적 단위, 장애물 분류, 실제 바닥/벽 추가, 성공 시 결제/실패 롤백, 저장·재실행. 난이도 높음. 카페/병원은 데이터 구조 공유만 준비. 이전은 설계만.
6. HUD 전체 — 검증된 공통 창을 상단/하단 메뉴와 연결. 기존 기능/캐릭터 UI/input raycast 유지, 두 Canvas 입력 중복 방지, 해상도/터치 크기 확인. 난이도 중간.
7. 통합 환경 테스트 — 별도 시각 환경에서 바닥·흙·돌·강·강둑·식생 A/B, shader/geometry/overdraw·드로우콜 확인. 난이도 중간~높음.
8. 자연환경 전체 적용 — 비교 결과에 따른 채택안만 최소 범위 적용, 기존 경로/건물/도로/저장/수역/충돌 보호. 난이도 중간~높음. 전체 적용이라는 이유로 미래 증축 부지를 강제 비우지 않는다.
9. 최종 검증 — 캐릭터/커스터마이징/카메라/NPC/펫, 건설·도로·실내 배치·증축, 저장 복원, 물/다리(실제 존재 시), UI 버튼과 해상도·성능. 난이도 높음.
각 단계는 별도 백업·변경 파일·검증 결과를 남긴다. 최근 사용자의 지시에 따라 범위 안의 통상적인 무료 다운로드/압축 해제/Import/검증은 반복 승인 없이 진행할 수 있으나, 유료 구매·데이터 삭제 등은 별도 확인 대상이다. 현재 통합 지시서의 즉시 요청은 분석이므로 이 보고서 단계에서는 새 UI/실내/증축 코드를 구현하지 않았다.

## 검증 범위와 현재 남은 오류
- 기존 건설 계획 5·6단계의 실제 Play/저장 왕복 결과는 별도 완료 보고서와 test-results.json에 있다. 이 통합 UI·실내·증축·자연환경의 새 기능을 실행 검증한 것으로 혼동하면 안 된다.
- 이번에는 Unity MCP의 scene/pipeline/asset/mesh/material/폰트 정보, 프로젝트 소스, 실제 pack 파일/라이선스를 분석했다.
- 허용된 OBJ 테스트: bathroomCabinet.obj를 AssetDatabase.ImportAsset으로 실제 등록했다. UnityEditor.ModelImporter, 정점 100/삼각형 108, URP/Lit 재질 및 원본 OBJ/MTL 해시 동일을 확인했다. 새 씬에 배치하거나 기존 게임에 사용하도록 바꾸지 않았다.
- 신규 폴더 등록과 함께 Furniture Pack의 .blend가 자동 Import되어 Blender 미설치 오류가 기록됐다. 이는 C# 컴파일 오류가 아니다. FBX/OBJ 대체본을 사용할 수 있다. Blender를 설치하거나 .blend를 임의로 옮기지 않았다.
- 분석 도구의 공통 mainTexture 질의가 GroundBlend의 없는 _MainTex에 접근한 로그 1건도 있었다. 이후 지면은 실제 _TexDirt 등 전용 프로퍼티로 조회했다. 게임 셰이더/소스를 바꾸지 않았다. 따라서 현재 Console 전체가 0오류라고 보고하지 않는다.
- 새 인터페이스 해상도, 11종 실제 통행 시안, 증축 롤백, 새 환경 FPS/모바일 GPU는 아직 미검증이다. 설치한 모든 물 셰이더가 목표 수면에서 정상 렌더된다고 단정하지 않는다.
- 최종 편집 씬은 미변경(isDirty=false), Play 중지 상태이며 원본 저장 데이터는 도로 단계 테스트 종료 시 복구된 상태를 유지한다.
